我想要的開發節奏是這樣：人帶著手機出門，Mac mini 留在桌上。有新單進來，需求清楚的小修改可以先做到測試環境；真的要我做決定時，手機上看得到一個可以回答的問題。我把這套跟 Claude 一起做的流程叫「無限開發」。這裡的「本機」指的是收單程式、工作目錄和 Git 都在我的 Mac 上；Claude Code 仍然要連線。

其實，前面那句「人帶著手機出門」，有一段慢慢累積的過程 XD。我回頭查了一下，**大約從 2025 年 8 月開始，我就陸續寫 Markdown 文件；到了 2026 年 1 月 5 日，才開始認真整理 skills**。一路做到現在，我跟 Claude 在各個專案一張單一張單地磨合，把反覆用到的做法留下來。每個專案有自己的商業邏輯：同一個詞在不同流程裡是什麼意思、畫面上的值從哪裡來、改了它還有誰會讀。我們把這些資料關係、架構細節和驗證方法留下來，下次開新對話也接得上。

**Memories** 留下的則是我們怎麼一起工作。我用手機看進度時，希望它把還沒驗的地方講清楚；如果有兩種合理的做法，我希望它先說自己傾向哪一種、理由是什麼，再讓我選。這些習慣都是做過幾次、我糾正過幾次，彼此才磨出來的。現在多數工作已經能讓 AI 自己往前做，我很少需要一路盯著。這份放心，來自一路累積下來的默契。巡單程式只是把這套合作方式接起來。

偶爾還是會發生一種狀況：**我心裡預期的假設，跟 AI 採用的假設不一樣。** 對我來說很自然的前提，可能根本沒說出口；AI 也可能依照另一種理解，把程式一路做下去。遇到這種落差，我會特別把自己的認知講清楚，包括我預期的情境、為什麼這樣判斷，以及怎樣的結果才符合需求，再讓它接著做。

沿用下面的虛構食譜例子，我可能一直覺得「料理時間」包含備料，AI 卻依照既有欄位，只算加熱時間。這時我得補上的就是「我認為這個時間要讓讀者拿來判斷多久能上桌」。把這個前提說出來，才能一起討論欄位和畫面要怎麼改。這類認知對齊，也是我跟 AI 持續磨合的一部分。

這一年裡，AI 的能力也一直在變。隨著模型和開發工具進步，原本需要我一步一步補充上下文、指導下一步的工作，逐漸能交給 Agent 自己讀程式、修改和執行驗證。專案知識與合作習慣的累積，也因此能用在更長、更完整的任務上。

從早期 Markdown 文件到認真整理 skills，再到現在的合作方式，是我實際走過的歷程。每個人從零開始需要的時間會不同。今天重新搭這套流程，可以沿用更成熟的工具，也可以先把已經知道的規則整理好。需要多久，仍取決於專案複雜度、既有文件，以及驗收標準是否清楚。

回頭看，我現在花更多心力想的是：**哪些事情可以授權 Agent 自己完成？我要拿什麼證據，確認它真的做對了？** 能改出程式之後，還要知道它有沒有理解需求、影響其他流程，以及測試結果究竟涵蓋了哪些情境。這也是我把工作分級、留下結果檔，再審查實際差異的原因。

拿一個虛構的食譜網站來說。假設有人開單寫「食譜列表要看得到料理時間」。如果資料裡已經有分鐘數，只差列表沒顯示，改一個畫面就能交差。但如果那個數字只有爐火加熱的時間，要不要把前一晚醃肉的八小時也算進去？程式跑得再快，也替我決定不了「料理時間」的意思。這兩種單在看板上長得一樣，我卻希望 Mac 收到之後做不同的事。

### 讓收單程式和開發對話各有自己的時鐘

我把流程拆成兩段。在 macOS 上，常駐的 Python 程式定時讀取工作看板，把單的內容存成本機快照，再把分析結果寫成檔案。另一端由 Claude 的**主工作階段**定時讀這些結果，判斷要報告、要問我，還是可以開始改程式。收單的程式持續運作時，就算我關掉開發對話，分析也可以先累積在磁碟上。

這裡有個小細節：我需要記得的其實是「哪一版已經跟我說過」。食譜那張單今天只寫了「顯示時間」，明天補上「用既有欄位，空值留白」，單號相同，能不能動手卻有了不同答案。我的做法是每張單只取最新一份分析，再拿它的檔名和本機 JSON 裡的紀錄相比。核心邏輯可以寫成這樣，下面是簡化示意：

```python
for task_id, report in latest_reports.items():
    if reported_versions.get(task_id) == report.name:
        continue
    notify_owner(report)
    reported_versions[task_id] = report.name
    save(reported_versions)
```

順序是先報告，再記帳。中間如果剛好中斷，下一輪可能再提醒一次。這個取捨我可以接受；反過來，先標記處理過、接著通知失敗，我就可能一直不知道那張單在等我。

### 綠燈能改到哪裡，黃燈要問什麼

| 收到的單 | 我讓 Claude 做到哪裡 |
| --- | --- |
| 綠燈：已有料理分鐘數，只要顯示在列表，空值行為也寫清楚了 | 確認現有版本還沒做，才進單一專案修改、驗證。主工作階段審過差異後，可推到測試環境。 |
| 黃燈：「料理時間」可能指備料、加熱或總耗時 | 先查現有欄位和畫面，回來問我「沿用詳情頁的加熱分鐘，還是要顯示含備料的總時間？」我用手機就答得了。 |
| 紅燈：要新增資料欄位、回填舊食譜，還要讓不同服務一起改 | 先列影響範圍和拆法，等人做設計決定。 |

我特別加了一步：**先去看現在的程式到底會怎麼跑**。一張單還掛在看板上，不代表功能一定還沒做。有時詳情頁已經有同一套顯示邏輯，有時測試分支甚至已經修好。只搜提交訊息裡有沒有單號，很容易漏掉這兩種情況。

### 一張單一個工作階段，做完交回差異

主工作階段負責巡單和分工。遇到能動手的單，就另外開一個 Claude 工作階段，交給它需求、允許修改的專案、目標分支和驗證方式。**同一個 Git 工作目錄一次只進一張單**，不同專案才平行。兩個對話各自有記憶，但它們如果共用同一個目錄，看到的是同一批尚未提交的檔案。

開工前先抓遠端分支的最新狀態。本機如果只是落後，同步腳本就用 Git 的 fast-forward 把分支移到新版；如果兩邊各自有新的提交，就保留現場，交給人看。推送前再查一次，因為我改食譜列表的這段時間，別人也可能剛好改了同一頁。

單張工作的終點是一份結果檔和本機提交。結果檔要寫清楚「改了什麼、驗了什麼、哪裡還沒驗」。例如桌面列表確實顯示「25 分鐘」，但手機版還沒看過，兩件事要分開寫。主工作階段收到後，對照實際的 Git diff 和驗證結果，才決定能不能推測試環境。遇到建置失敗、衝突或混進別張單的改動，就停下來。正式發布仍由我決定。

### 對話結束後，下一班要接得起來

這套東西有個很實際的限制：巡單排程跟著主工作階段走。Mac 重開或工作階段結束，就要重新啟動巡單。所以我把「等待我回答的問題、做到一半的單、還在排隊的單」列為交接內容。定時換新工作階段、讀交接檔再接手，是我已經寫進流程的設計；每天自動換班這段還沒完整驗過。

做完這套之後，我最在意的是手機收到的那一句話。如果它只說「需求不清楚」，我還是得回桌前從頭讀。如果它能告訴我「詳情頁已經有加熱分鐘，列表要沿用，還是要加上備料時間？」，我在外面就能做決定，回家直接看改好的畫面。這才是我想從「無限開發」拿回來的時間。
